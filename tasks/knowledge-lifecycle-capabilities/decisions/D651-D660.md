# Decisions D-651–D-660

### D-651 — Source provenance is opt-in; successful Collection does not require a Source anchor

- **Corrects D-245's Collection invariant, not its lazy-anchor topology**: withdraw “no newly collected graph may omit Source provenance.” A Collection may commit domain Blocks/Relations successfully while `sources.block` remains `NULL`. Source is an operational acquisition/execution context, not automatically a participant in the knowledge facts it obtains.
- **Value test before projection**: a producer creates a Source-anchored Relation only when the Source itself has a useful, independently consumed relationship to another graph entity. “This Source happened to fetch this Block” is not sufficient by default; do not persist `collects` for every admitted Post, User, Media or other item merely to form a collection ledger or facilitate inverse traversal. A provider returning a field/fact is also insufficient reason to persist it.
- **The domain actor owns domain behavior**: a Twitter account `--bookmarks-->` Post and a GitHub account `--stars-->` Repository are account-level facts, regardless of which operational Source fetched them. A generic `Source --collects--> Twitter/GitHub Account` is not required merely to anchor these domain relations; its usefulness must be demonstrated independently. Source state / Job diagnostics may serve execution needs without being promoted wholesale to the info-base.
- **Source relationships are not banned**: a Mail Source `--manages-->` a Source-scoped Mailbox may remain necessary to represent a real management/access path, including later remote materialization. Other Source-bound relations may likewise qualify on their own merits; this decision neither removes those contracts nor mandates that every Source type be anchorless.
- **Retain D-245–D-247's opt-in mechanism**: when an admitted producer actually needs a Source Block as a Relation endpoint, `SourceManager.ensure_block_async` still lazily creates/reuses one stable `core.source.v1` anchor in the caller-owned transaction and refreshes its descriptor. The uniqueness, concurrency, SourceModel authority/projection and identity/lifecycle contracts are unchanged. Do not create an anchor merely because a Collection starts or commits.
- **Retain D-242's historical-survival rule**: deleting an operational Source does not delete any already-existing Source Block, admitted Relation or collected domain fact. This preservation rule is conditional on such graph objects having been created; it does not impose a provenance-creation duty.
- **No speculative migration**: do not mass-delete previously written provenance, alter Source schema, retrofit a generic provenance service or rewrite unrelated producers under this decision. Each affected extension must assess its actual consumer and migration needs in a separate implementation scope. In particular, Twitter Issue [#184](https://github.com/InKCre/impl-py/issues/184) owns its own `User --bookmarks--> Post` implementation; any GitHub `Source --collects--> Account` simplification is separate.
- **Verification boundary**: a domain-only collector can be accepted by asserting its persisted domain facts without expecting a Source anchor. For producers that do require Source-anchored relations, verify those producer-owned facts; do not repeat generic info-base graph-navigation guarantees in every vertical.
- **Relationship to earlier decisions**: supersedes only D-245's blanket Collection invariant and clarifies the D-241 direct-`collects` example as an optional grammar when provenance has earned persistence. D-242 and the rest of D-245–D-247 remain in force.
- **Confidence**: accepted after reviewing Twitter PR #194's Source-scoped implementation and the independent value of its proposed relations. The correction is to the general product boundary, not a finding that existing Source anchor APIs are defective.
